# Listflow

AI-powered eBay listing assistant for resellers. Snap photos of items → AI identifies the item, suggests a title and pricing → review and post to eBay.

## Tech Stack

| Layer | Tech |
|---|---|
| Framework | Next.js 14.2.35 (App Router, TypeScript) |
| Styling | Tailwind CSS |
| Icons | Lucide React |
| AI | OpenAI GPT-4o-mini (vision) |
| Database | Supabase (PostgreSQL) |
| Deployment | Vercel |

Environment variables required:
- `OPENAI_API_KEY` — server-side only
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `EBAY_CLIENT_ID`, `EBAY_CLIENT_SECRET`, `EBAY_RUNAME` — the one registered eBay application, correctly shared across all users (each user still does their own OAuth consent against this one app — see the Phase 2 note below).
- `EBAY_TOKEN_ENCRYPTION_KEY` — 32-byte, base64-encoded AES-256-GCM key used to encrypt each user's eBay refresh token before it's stored in `ebay_connections`. Generate with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` and paste directly into Vercel — never share it elsewhere.
- `SUPABASE_SERVICE_ROLE_KEY` — server-side only, never sent to the browser. Used by `/api/auth/lockout` (a thin proxy for the three login-lockout RPCs — see the Security hardening note below) to call Postgres functions that are no longer grantable to `anon`/`authenticated`. Get it from Supabase dashboard → Settings → API → service_role key, and paste directly into Vercel — never share it elsewhere; it bypasses RLS entirely.
- `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` — optional. Powers rate limiting across the API surface (see below). If unset, rate limiting is silently skipped rather than the app failing.
- `NEXT_PUBLIC_SENTRY_DSN` — optional but set. Sentry error monitoring (see below). Not a secret — Sentry DSNs are designed to be public (they can only submit events to this project, never read anything back) and this one is intentionally a `NEXT_PUBLIC_` var so the browser-side config can use it too.
- `CRON_SECRET` — required for the account-deletion purge job (`GET /api/cron/purge-deleted-accounts`) to accept requests. Vercel automatically sends `Authorization: Bearer $CRON_SECRET` on its own Cron-triggered requests once this env var is set — generate any random string (e.g. `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`) and paste it into Vercel; it isn't used anywhere else.

**Deprecated as of Phase 2 (per-user eBay connections) — no longer read by the app, safe to remove from Vercel whenever convenient:** `EBAY_OAUTH_REFRESH_TOKEN`, `EBAY_SHIPPING_FREE_ID`, `EBAY_SHIPPING_HEAVY_ID`, `EBAY_SHIPPING_CALCULATED_ID`, `EBAY_RETURN_POLICY_ID`. These used to be one shared seller connection/policy set for the whole app; each user now connects their own eBay account and picks their own policies in Settings → eBay Connection.

## What's Built

### Pages
- `/` — Landing/splash page
- `/login` — Supabase sign-in/sign-up
- `/dashboard` — Live stats (drafts, active listings, weekly revenue + sold count) + quick action cards. "To ship" card shows urgent badge when items are awaiting shipment.
- `/new-listing` — Single item flow: 3-photo slots (front, measurements, flaws) → AI analysis + live pricing in parallel → save draft / list on eBay
- `/batch-upload` — Multi-item workflow: upload → AI photo grouping → manual review → bulk analysis → results with bulk list/save actions
- `/drafts` — Unlisted drafts with thumbnails, pricing info, no-price warning, bulk delete, bulk list with price guard
- `/drafts/[id]` — Edit draft, AI suggest specifics, re-analyze with new photos, list / relist on eBay
- `/store` — Active + recently-ended eBay listings (Supabase + eBay merged), tabbed. Active tab: search, sort, inline price edit, bulk price update, delist. Ended tab: read-only, "Relist on eBay" link (eBay only retains a recent window of ended-unsold listings — there's no way to widen that from our side).
- `/sales` — Sales history with 7d/30d/90d/1y toggle, total revenue, per-item thumbnails
- `/ship` — Items paid but not yet shipped: buyer name/address, days-since-payment badge, Ship → link to eBay order
- `/membership` — Pricing plans UI only (Stripe deferred)
- `/privacy`, `/terms` — real Privacy Policy / Terms of Service content (rewritten Sept 3, 2026 from a four-paragraph placeholder — see the Legal content bullet below), public (no login required). Linked from the landing page footer, a consent line on `/login`, and a Legal footer on `/settings` — none of which existed before.
- `/settings` — App-wide defaults, redesigned Sept 2, 2026 into distinct cards (each with an icon badge header, via `SettingsSection` in `src/app/settings/page.tsx`) instead of plain stacked text labels: **Default shipping** (Free / Calculated, every new listing starts on this), **eBay Connection** (connect/reconnect, Business Policy pickers), **Appearance** (Light / Dark / System — see Theming below), **Account** (sign out; Danger zone → Delete account, see the account-deletion note below). Linked from a gear icon on `/dashboard`.
- `/account/pending-deletion` — the only page a signed-in user with a pending deletion request can reach; shows a day countdown and a one-click Reactivate (see below).

### API Routes
- `POST /api/analyze-item` — GPT-4o-mini vision, 1–3 photos; returns itemType, brand, color, size, condition, flaws, title, style, material, pattern, fit, vintage, theme, character, yearManufactured, season, description, and measurements (pitToPit, length, waist, inseam read from measuring tape in photo)
- `POST /api/analyze-batch` — Sequential batch analysis with rate limit handling and retry logic
- `POST /api/group-photos` — GPT-4o clusters mixed uploaded photos into per-item groups
- `GET|POST|DELETE /api/drafts` — Supabase CRUD for saved drafts
- `GET /api/drafts/[id]` / `PATCH /api/drafts/[id]` / `DELETE /api/drafts/[id]`
- `POST /api/ai/suggest-specifics` — fills eBay item specifics from existing draft fields
- `POST /api/pricing/suggest` — live pricing via eBay Browse API (image search → text fallback → condition-adjusted median)
- `GET /api/ebay/ship` — paid-but-unshipped orders from GetSellerTransactions
- `GET /api/ebay/sales?days=7|30|90|365` — sales history (multi-window, chunked into 30-day GetSellerTransactions calls and merged; capped at 365 days)
- `GET /api/ebay/store` — active + ended-unsold listings via GetMyeBaySelling (ActiveList + UnsoldList, each independently paginated)
- `GET /api/ebay/inventory` — Supabase-sourced listings (instant load for store page)
- `POST /api/ebay/list` — full listing flow: upsert inventory → create/update offer → publish
- `POST /api/ebay/delist` — end listing, clear from Supabase
- `POST /api/ebay/update-price` — ReviseFixedPriceItem + update Supabase
- `GET /api/ebay/connect` / `GET /api/ebay/callback` — OAuth flow
- `GET /api/dashboard/stats` — aggregated stats for dashboard
- `POST /api/auth/lockout` — server-side proxy for the three login-lockout Postgres RPCs (`check`/`record`/`clear` actions), called from `/login` before/after `signInWithPassword`. Exists so those RPCs can be locked down to `service_role` only instead of staying callable by anyone via Supabase's public REST RPC endpoint — see the Security hardening note below.
- `GET|PATCH /api/settings` — reads/writes the per-user `app_settings` row (`default_shipping_mode`, `deletion_requested_at`)
- `POST /api/account/delete` — starts the 30-day account-deletion grace period; deletes nothing itself
- `POST /api/account/reactivate` — cancels a pending deletion request
- `GET /api/account/status` — pending state + days remaining, used by Settings and `/account/pending-deletion`
- `GET /api/cron/purge-deleted-accounts` — Vercel Cron only (`CRON_SECRET`-gated); permanently deletes any account whose grace period has elapsed
- `GET /api/ebay/store-categories` — fetches the seller's eBay Store custom categories (Trading API `GetStore`), flattened to leaf categories with a "Parent / Child" display path; returns `{categories: [], connect: true}` if eBay isn't connected

### Notable Implementation Details
- **node:https for all eBay + OpenAI calls** — Next.js 14 patches `globalThis.fetch` which breaks repeated outbound HTTPS. All external API calls use `node:https` directly. Every route using it must export `runtime = "nodejs"`.
- **eBay Trading API URL**: `https://api.ebay.com/ws/api.dll` (not `/ws/services`)
- Client-side image resizing before upload (max 1568px) to reduce API token cost
- Batch upload uses explicit step state machine: `upload → grouping → review → analyzing → results`
- **Batch processing is bounded-concurrency, not fully sequential.** `/batch-upload`'s AI analysis pool (`ANALYSIS_CONCURRENCY` in `src/app/batch-upload/page.tsx`) runs 3 items at once — the same worker-pool pattern already used for its pricing lookups (`PRICING_CONCURRENCY`) — instead of one at a time; bulk "List on eBay" (`LISTING_CONCURRENCY`) runs 2 at once, kept lower since a single listing is already several sequential eBay calls internally. `/api/analyze-batch` itself still retries each item up to 3 times with a 15s backoff on an actual OpenAI rate-limit response — that safety net is unchanged, it just now backs up 3 lanes instead of 1. The real ceiling on how much this can help is OpenAI's own per-minute token budget on the account (visible in a 429's error text), not something raising these numbers further can fix on its own.
- AI measurements injected as first line of `description` field — not stored as separate DB columns
- GetSellerTransactions requires `<DetailLevel>ReturnAll</DetailLevel>`, but — despite what an earlier version of this doc claimed — its `<Item>` block never includes `PictureDetails`/`GalleryURL` no matter the DetailLevel (confirmed against eBay's own docs, which list GetSellerTransactions' limited Item fields explicitly and point to `GetItem` for anything more). `/api/ebay/sales` gets sold-item thumbnails from two places instead: the Supabase `drafts.thumbnail_url` for anything listed through this app (instant, no extra call), and a `GetItem` call per remaining ItemID (concurrency-limited to 5, capped at 60 lookups per page load) for older/manually-listed items with no Supabase row. Note eBay stops returning item details (pictures included) for listings that ended more than ~90 days ago, so some very old sales can still show the placeholder icon — a real eBay limitation, not a bug.
- GetSellerTransactions ModTime cap is 30 days — anything beyond that (up to the 365d cap) uses parallel window calls merged with dedup. **Fixed Sept 3, 2026:** those merged results were never sorted, so /sales rendered sales in whatever order the parallel per-window calls happened to resolve in (visibly out of date order once more than one window was involved) instead of most-recently-sold first. `/api/ebay/sales/route.ts` now explicitly sorts by `soldAt` descending after the merge.
- GetMyeBaySelling's `ActiveList` only ever returns *currently active* listings — it never included ended/unsold ones. `/store` now also requests `UnsoldList` (same pagination pattern, independent totals) so "ended without selling" listings are visible too, not just active ones. Sold listings still live only under `/sales` (GetSellerTransactions), not here.
- **Shipping mode, fixed Sept 3, 2026 — this doc used to describe a `ShippingModeControl` three-way toggle that was never actually in the codebase.** `shippingMode: "free" | "buyer_pays" | "calculated"` (`src/lib/shipping.ts`; parsed from request bodies with `parseShippingMode`). Reality found during a New Listing flow bug audit: none of the three listing screens (new-listing, batch-upload per item, drafts/[id]) has ever had a mode picker — each only has a plain "Heavy item" checkbox + a $ shipping-cost field, and none of them sent `shippingMode` at all in the `POST /api/ebay/list` body. Since the route silently defaulted missing `shippingMode` to `"free"`, **every listing ever created through this app shipped on the Free Shipping policy**, no matter what a seller picked as their Default Shipping Mode in Settings (`app_settings.default_shipping_mode`, Free/Calculated) — that setting did nothing — and checking "Heavy item" never applied the flat-rate "buyer pays" policy or cost override on the real eBay listing, it only nudged the suggested price. Fixed server-side in `/api/ebay/list/route.ts` (one place, covers all three screens since they share this route) instead of building the missing UI control: when the request doesn't specify `shippingMode` explicitly, a checked "Heavy item" (`isHeavy: true`, already sent by every screen) now resolves to `"buyer_pays"`, otherwise the seller's own saved Settings default is looked up and used. A real per-item three-way toggle (so "Calculated" can be chosen per listing, not just as a global default) remains a nice-to-have, not yet built. This threads into pricing (`computeListAndFloor` in `src/lib/pricing.ts`) and into the actual eBay setup applied:
  - **Free**: seller's own "free shipping" policy (picked in Settings → eBay Connection, stored in `ebay_connections.shipping_free_policy_id`); full estimated shipping cost baked into the item price before grossing up for eBay fees.
  - **Buyer pays (flat)**: seller's own flat-rate "buyer pays" policy (`shipping_heavy_policy_id`) with a `shippingCostOverrides` set to the seller-chosen dollar amount; item price only needs to recover the *fee portion* of that shipping charge (buyer fronts the cost itself) — real margin the "free" math would otherwise absorb.
  - **Calculated**: seller's own "cost varies by buyer location" policy (`shipping_calculated_policy_id`) plus a `packageWeightAndSize` (weight + box dimensions + `packageType`) attached to the inventory item itself (`upsertInventoryItem` in `src/lib/ebay-inventory.ts`) so eBay can quote each buyer their own real carrier rate at checkout. No dollar override is sent (or possible) for this mode — same fee-only pricing treatment as buyer-pays, using the app's weight estimate as the best available proxy since the real per-buyer charge isn't known ahead of time.
  All three policy IDs (plus the return policy) come from `getEbayContext().policies` (`src/lib/ebay-request-context.ts`), populated per-request from that user's `ebay_connections` row — see the Phase 2 note below. Before Phase 2, these were one shared set of env vars.
  Both the cost estimate and the calculated-mode package weight/dimensions come from `src/lib/shipping.ts`'s weight-based estimate (`estimateShipping`/`estimatePackage`, from AI-detected item type/size/material against USPS Ground Advantage weight breaks and reasonable per-weight-bracket box sizes) — an estimate, not a measurement, same tradeoff as before.
- All eBay-dependent pages return `connect`/`reconnect` flags for missing/expired token UI
- **eBay Store Categories are AI-suggested, never auto-applied.** Every listing screen (new-listing, batch-upload per item, drafts/[id]) shows a `StoreCategoryControl` dropdown of the seller's real Store categories (from `GET /api/ebay/store-categories`, only leaf categories — eBay silently reroutes items assigned to a parent category to "Other"). During AI analysis, `buildItemVisionPrompt()` (`src/lib/vision-prompt.ts`) is built dynamically with the seller's actual category names spliced in, so GPT-4o-mini picks from a real, current list instead of guessing; the match is shown pre-selected in the dropdown with an "AI suggested" badge (which disappears the moment the seller picks something else — never a silent auto-apply). The choice is saved on the draft (`store_category_id`/`store_category_name` columns) and, once the listing is actually published and has a real eBay ItemID, applied with a best-effort `ReviseFixedPriceItem` call (`setListingStoreCategory` in `src/lib/ebay-store-categories.ts`) — if that call fails, listing still succeeds and a non-blocking `storeCategoryWarning` is surfaced on-screen rather than silently swallowed. Category data is cached in memory for 30 minutes (`fetchStoreCategories`) since `GetStore` is a relatively heavy call and categories rarely change mid-session. Scope: new listings only — this does not retrofit categories onto already-live eBay listings.
- **Rate limiting, two tiers, across the whole API surface** (`src/middleware.ts`, Upstash Redis via `@upstash/ratelimit`/`@upstash/redis`) — not just the two AI vision endpoints anymore. Tier 1 (15 req/min/IP): every endpoint that triggers a real paid OpenAI call or fans out several eBay calls per invocation — `/api/analyze-item`, `/api/analyze-batch`, `/api/group-photos`, `/api/ai/suggest-specifics`, `/api/pricing/suggest`. Tier 2 (60 req/min/IP): every other `/api/*` route (excluding the eBay OAuth callback), a catch-all that used to have zero rate limiting at all. Built defensively: if `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` aren't set, rate limiting is silently skipped rather than crashing every request through middleware — a missing secondary feature should never take down the whole app.
- **Per-user data isolation (Phase 1 of the multi-tenant plan, shipped).** `supabase-migrations/003_multi_tenant_isolation.sql` converted `drafts.user_id` from dead `text default 'default-user'` to a real `uuid` FK against `auth.users(id)`, rewrote RLS on `drafts`/`app_settings`/the `photos` storage bucket to be scoped to `auth.uid()` instead of just "authenticated," and converted `app_settings` from one shared singleton row to one row per user (auto-created on first Settings save via upsert in `/api/settings`). Photo uploads are namespaced by user folder (`src/lib/storage.ts`) to match.
- **Per-user eBay connections (Phase 2 of the multi-tenant plan, shipped).** `supabase-migrations/004_ebay_per_user_connections.sql` adds `ebay_connections` (one row per user: encrypted refresh token, own Business Policy IDs). Each eBay-touching API route calls `requireEbayConnection()` (`src/lib/ebay-connection.ts`) then runs its logic inside `ebayContext.run(...)` (`src/lib/ebay-request-context.ts`, a Node `AsyncLocalStorage`) instead of every function in `ebay-inventory.ts`/`ebay-store-categories.ts` taking a userId parameter — `getAccessToken()` and the Store Category cache read the connection from that implicit per-request context, keyed by userId internally so two users' requests landing on the same warm serverless instance can never cross-contaminate tokens/categories. The refresh token is encrypted at rest (`src/lib/ebay-token-crypto.ts`, AES-256-GCM via `node:crypto`, key in `EBAY_TOKEN_ENCRYPTION_KEY`) — `/api/ebay/callback` stores it there directly now instead of displaying it for manual copy-paste into an env var. Business Policies (shipping/return) are picked in Settings → eBay Connection from a live list fetched via eBay's Account API (`/api/ebay/policies`, `sell.account.readonly` scope), same "seller picks from what's actually theirs" pattern as Store Categories. **The one eBay app registration itself** (`EBAY_CLIENT_ID`/`SECRET`/`RUNAME`) stays a shared env var — that's normal, it's the app every user OAuths into, not a seller-specific credential. Anyone connected before this scope was added needs to reconnect once (Settings → Reconnect) to pick it up.
- **Security hardening pass (Sept 2026).** Four fixes from a full code + Supabase-advisor audit: (1) HTTP security headers (CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, HSTS) added via `headers()` in `next.config.js` — previously there were none at all; (2) rate limiting extended from 2 routes to the whole API surface, see the bullet above; (3) `store_category_id` is now validated as a numeric string at both API boundaries that accept it (`POST /api/drafts`, `PATCH /api/drafts/[id]`) — it was always eBay-numeric and always dropdown-picked, never hand-typed, so a non-numeric value only ever meant a bug or a tampered request; `/api/drafts/[id]`'s GET/PATCH/DELETE also gained an explicit `.eq("user_id", ...)` check alongside RLS (belt-and-suspenders against a cross-account ID guess), same for the bulk delete in `/api/drafts`; (4) the three login-lockout Postgres functions (`check_login_lockout`/`record_failed_login`/`clear_login_attempts` — see the `login_attempts` table note below) were revoked from `anon`/`authenticated` and re-granted to `service_role` only (`supabase-migrations/006_lock_down_login_rpcs.sql`) — they used to be callable by anyone directly against Supabase's public REST RPC endpoint with zero rate limiting, including to lock a real user out by spamming `record_failed_login` for their email. `/login` now calls a new `POST /api/auth/lockout` route instead, which proxies those three RPCs with a `SUPABASE_SERVICE_ROLE_KEY` client — so every call is now subject to the app's own rate limiting like everything else.
- **No self-service sign-up, still on purpose (for now).** `/login` only offers sign-in, never account creation — see the comment at the top of `src/app/login/page.tsx`. The two legitimate accounts were created directly in the Supabase dashboard. **The UI change alone is not sufficient** — "Allow new users to sign up" should also be disabled in the Supabase dashboard (Authentication → Sign In / Providers → Email), since that's enforced by Supabase itself and can't be bypassed by calling its REST API directly with the public anon key the way an app-level check could be. Sign-up stays closed for now regardless — the owner is running a personal test period before deciding to open it, independent of whether the technical guardrails below are in place.
- **Phase 3 spending safety net, shipped Sept 3, 2026 — a hard per-account monthly AI usage cap.** `supabase-migrations/010_ai_usage_cap.sql` adds `ai_usage_counters` (one row per user: `period_month`, `call_count`) plus a SECURITY DEFINER function `check_and_consume_ai_usage(user_id, amount, monthly_limit)` that atomically checks-and-increments, resets automatically when the calendar month rolls over, and is locked down to `service_role` only — same pattern as the login-lockout RPCs (005/006/007), unreachable from the browser or Supabase's public REST RPC endpoint. `src/lib/ai-usage.ts` wraps it (`checkAndConsumeAiUsage`, `MONTHLY_AI_CALL_LIMIT = 400/month`, tunable without a migration) and fails open on any Supabase error, matching the fail-open choice already made for Upstash rate limiting when its env vars are unset. Wired into all four OpenAI-calling routes: `/api/analyze-item`, `/api/group-photos`, and `/api/ai/suggest-specifics` each consume 1 call and return a 429 with a plain-English message once the cap is hit; `/api/analyze-batch` consumes one call per group in the batch (not one per request) and, if a batch doesn't fully fit the month's remaining budget, processes as many groups as still fit and marks the rest capped in the results array — rather than failing the whole batch over a partial shortfall. This removes the last technical blocker to opening sign-up (see the bullet above) — the decision to actually open it is still the owner's, separate from whether it's safe to.
- **Self-service account deletion, with a 30-day grace/reactivation period (shipped Sept 2, 2026, once Phase 1's per-user data isolation made it safe).** An earlier `DELETE /api/user/delete` route was deliberately left unmerged because, pre-Phase-1, `drafts` had no per-user ownership column — deleting "your own" data would have deleted everyone's. That's fixed now (see the Phase 1 bullet above), so this shipped as a real soft-delete flow rather than an instant, irreversible one: Settings → Account → Danger zone → Delete account (`POST /api/account/delete`) just timestamps `app_settings.deletion_requested_at` and signs the user out — nothing is actually deleted yet. `src/middleware.ts` then locks any signed-in user with that flag set to `/account/pending-deletion` (and the couple of API routes that page itself calls) until they either hit "Reactivate" there (`POST /api/account/reactivate`, clears the flag) or the grace period (`ACCOUNT_DELETION_GRACE_PERIOD_DAYS = 30`, `src/lib/account-deletion.ts`) elapses. A daily Vercel Cron job (`vercel.json`, hits `GET /api/cron/purge-deleted-accounts`, gated on the `Authorization: Bearer $CRON_SECRET` header Vercel sends automatically) finds accounts past that window, deletes their `photos` storage files by hand first (storage objects aren't FK'd to `auth.users`, so it's the one thing that isn't automatic), then calls `supabase.auth.admin.deleteUser()` — which cascades to `drafts`, `ebay_connections`, and `app_settings` for that user alone via the `on delete cascade` FKs from migration 003. One account's cleanup failing doesn't block the rest of that day's batch; it's simply retried on the next run since `deletion_requested_at` stays set until the delete actually succeeds. Migration: `supabase-migrations/008_account_deletion.sql`.

- **RLS query-plan performance fix, Sept 3, 2026.** A Supabase advisor scan (part of the same public-launch-readiness audit as the AI usage cap above) flagged `auth_rls_initplan` on every policy in `drafts`, `app_settings`, and `ebay_connections`: each called `auth.uid()` directly in its `USING`/`WITH CHECK` clause, which Postgres re-evaluates once per row instead of once per query — invisible with a handful of rows, a real cost once an account's row counts grow. `supabase-migrations/009_rls_performance.sql` rewrites all eleven policies to `(select auth.uid())`, which Postgres caches for the whole query. No access-rule change, confirmed clean on a re-run of `get_advisors`.
- **Theming (light/dark/system)** — CSS custom properties (`--bg-page`, `--bg-surface`, `--text-primary`, `--danger`, `--warning-bg`, etc. — see `src/app/globals.css`) are defined three times: once on bare `:root` (light, the default), once under `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-theme="light"])` (follows the OS/browser setting when the seller hasn't picked one explicitly), and once under `:root[data-theme="dark"]` (an explicit choice always wins, either direction). The choice is stored in a plain `theme` cookie (`src/lib/theme.ts`) — **not** localStorage — specifically so `RootLayout` (`src/app/layout.tsx`, a server component) can read it with `cookies()` and render the correct `data-theme` attribute into the very first byte of HTML. That avoids the "flash of wrong theme" that localStorage-based approaches need a blocking inline `<script>` in `<head>` to paper over. `.card`/`.btn`/`.btn-primary`/`.input` (used as plain classNames across ~20 files) live in the same file and are what actually give cards/buttons/inputs their background, border, and shadow — they read from the same variables, so they theme automatically too.

Net effect: every card/button/input in the app rendered with zero styling from those classes (whatever shape they had came only from other literal Tailwind utilities on the same element), and Settings → Appearance's Dark/System options changed the `data-theme` attribute correctly but nothing was listening for it, so the toggle visibly did nothing. Confirmed via `git log -p -- src/app/globals.css` (the stub's own commit message admits it wasn't the real file) and via grepping compiled output (`.next/static/css/*.css` had zero occurrences of `.card` before the fix, all expected rules present after). Restored the full variable set + component classes + dark-mode blocks; if a future device-access gap ever forces a placeholder file again, treat that placeholder as temporary and diff it back out before considering the fix done — don't let a stub become the permanent file a second time.

- **Error monitoring via Sentry, added Sept 3, 2026.** Free "Developer" tier (one user, error monitoring, email alerts — plenty for this app's scale). Deliberately minimal setup: `sentry.client.config.ts`/`sentry.server.config.ts`/`sentry.edge.config.ts` (browser, Node routes, and `src/middleware.ts`'s edge runtime respectively) all just call `Sentry.init({dsn, tracesSampleRate: 0})` — no performance tracing, and Session Replay was never enabled (this app's data — draft photos, shipping addresses — has no business being screen-recorded by a third party). `src/instrumentation.ts` is the Next.js hook that loads the server/edge configs; `src/app/global-error.tsx` catches anything that escapes every other error boundary and reports it before showing a plain "something broke" screen. `next.config.js` wraps the export with `withSentryConfig` (no `org`/`project`/`authToken` — those are only needed for source-map upload, a later optional upgrade, not something error capture depends on) and — important — had to add Sentry's ingest host to the CSP's `connect-src`, since the security-hardening pass's own lockdown would otherwise silently block the browser from ever reaching Sentry. `src/app/api/sentry-test/route.ts` is a standing, deliberately-broken route (`force-dynamic` so it doesn't fail the build trying to statically prerender something that always throws) for confirming events actually arrive — visit it once after deploying, check the Sentry dashboard, safe to leave in permanently.
- **New Listing / Batch Upload stale-draft bug, fixed Sept 3, 2026.** `/api/ebay/list` always builds the actual eBay listing from the draft's current row in the database, never from the request body — so anything that changes on screen after the draft was first saved only reaches eBay if it also reaches the database. `new-listing/page.tsx`'s `handleSaveDraft()` and `batch-upload/page.tsx`'s per-row `handleSaveDraft(index)` both used to short-circuit (`if (savedDraftId) return savedDraftId;` / `if (draftIds[index]) return draftIds[index];`) once a draft existed, turning every later call into a no-op — new-listing's "List on eBay" at least re-sent a narrow 6-field PATCH (title/brand/size/color/condition/price) on a repeat attempt, but batch-upload's didn't even do that. Either way, photos, AI-detected item type/description/style/material/etc., and (in new-listing) any field outside that narrow list were silently dropped: re-running Analyze, adding a photo, or editing a batch-upload row (title/condition/brand/color/size/flaws are all inline-editable there) after an initial save — including the very first "List on eBay" attempt if it failed and needed a retry, e.g. because eBay wasn't connected yet — meant the live listing shipped with stale, pre-edit data. Fixed by removing the short-circuit in both files: `handleSaveDraft` now always does a real sync (`POST` once to create, `PATCH` every subsequent call with the full current field set), and `handleListOnEbay` in both files now always calls it before listing instead of conditionally re-sending a subset. `drafts/[id]/page.tsx` (the edit-existing-draft screen) never had this bug — it always PATCHes its full field set before every "List on eBay" call, since it doesn't have a create-vs-update branch to short-circuit.
- **Store description footer, added Sept 3, 2026.** Settings → "Store description" is a free-text box (`app_settings.store_description_footer`, migration `011_store_description_footer.sql`) for a seller's standing boilerplate — welcome message, shop policies, a sign-off — written once instead of retyped into every listing. It's applied automatically and invisibly: `upsertInventoryItem` (`src/lib/ebay-inventory.ts`) appends it to the item's own description only at the moment the actual eBay listing body is built, joined with a blank line. It is never written into `drafts.description` itself, so an item's own description field always stays just that item's own details on every listing screen (new-listing, batch-upload, drafts/[id]) — none of them needed to change, since they all funnel through this one function via `/api/ebay/list`. The footer is looked up fresh on every "List on eBay" call (`/api/ebay/list/route.ts` reads `app_settings` alongside the existing default-shipping-mode lookup, one query for both), so editing or clearing it in Settings takes effect on the very next listing, not just future ones.
